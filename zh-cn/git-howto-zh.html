1 简介# TOC

本文档旨在提供一组常用 Git 命令的快速参考。你应当始终 使用 Git 直接提供的详尽而详细的 文档： 

git --help
man git

会显示可用的子命令， 

git <command> --help
man git-<command>

会显示关于子命令 <command> 的信息。

更多信息可以在 Git Reference 网站上找到。

想了解更多关于 Git 项目的信息，请访问 Git 网站。

遇到问题时请查阅这些资源，它们相当详尽。

接下来是 Git 的基本介绍以及一些 FFmpeg 特有的 指南，以便更轻松地为该项目做贡献。

2 基本用法# TOC

2.1 获取 Git# TOC

你可以从 http://git-scm.com/ 获取 Git 大多数发行版和操作系统都为其提供了软件包。

2.2 克隆源码树# TOC

git clone https://git.ffmpeg.org/ffmpeg.git <target>

这会把 FFmpeg 源码放入目录 <target> 中。 

git clone git@source.ffmpeg.org:ffmpeg <target>

这会把 FFmpeg 源码放入目录 <target>，并让你 把变更推送回远端仓库。 

git clone git@ffmpeg.org:ffmpeg-web <target>

这会把 FFmpeg 网站的源码放入目录 <target>，并让你把变更推送回远端仓库。

如果你对 ffmpeg-web 仓库没有写权限，你可以在 创建只读的 ffmpeg-web 克隆之后制作补丁： 

git clone git://ffmpeg.org/ffmpeg-web <target>

请确保你的检出中没有 Windows 换行符， 否则你可能会遇到莫名其妙的编译失败。实现这一点的 一种方法是运行 

git config --global core.autocrlf false

2.3 将源码树更新至最新修订版本# TOC

git pull (--rebase)

会从被跟踪的分支拉取最新变更。被跟踪的分支 可以是远端的。默认情况下，master 分支跟踪远端 origin 中的 master 分支。

推荐使用 --rebase（见下文）。

2.4 变基本地分支# TOC

git pull --rebase

会从主仓库获取变更，并把你的本地提交重放到 其上。这是让所有本地变更位于 FFmpeg master 树顶部的 必要做法。master 树会拒绝包含合并提交的推送。

2.5 添加/删除文件/目录# TOC

git add [-A] <filename/dirname>
git rm [-r] <filename/dirname>

Git 需要被告知你在工作目录中所做的、会导致文件出现或 消失的所有变更。 跨文件的行移动会被自动跟踪。

2.6 显示修改# TOC

git diff <filename(s)>

会以统一差异格式显示工作目录中的所有本地修改。

2.7 查看变更日志# TOC

git log <filename(s)>

你也可以使用诸如 gitview 或 gitk 之类的图形化工具， 或者访问 https://git.ffmpeg.org/ffmpeg.git 处的 Web 界面。

2.8 检查源码树状态# TOC

git status

会检测你所做的所有变更，并列出在提交的情况下将执行哪些 操作（新增、修改、删除等）。

2.9 提交# TOC

git diff --check

以便在提交前再次检查你的变更，避免日后出现 麻烦。所有有经验的开发者对每一次提交都会这样做，无论 改动有多小。

他们每个人都曾多次因此免于出丑。 多余的调试输出或表面性的修改很容易混入， 请通过这一额外层次的审查来避免问题。

对于只做表面修改的提交，你应当从下面这条命令得到（几乎）空的输出 

git diff -w -b <filename(s)>

还要检查以下命令的输出 

git status

以确保你没有未跟踪的文件或删除操作。 

git add [-i|-p|-A] <filenames/dirnames>

请确保你已经告诉 Git 你的姓名、电子邮件地址和 GPG 密钥 

git config --global user.name "My Name"
git config --global user.email my@email.invalid
git config --global user.signingkey ABCDEF0123245

启用对所有提交的签名，或使用 -S 

git config --global commit.gpgsign true

使用 --global 为你的所有 Git 检出设置全局配置。

Git 会选择文件中要提交的变更。你也可以选择使用 交互模式或补丁模式，逐个代码块地选择哪些内容应当 加入提交。 

git commit

Git 会把选中的变更提交到当前本地分支。

编辑器会提示你输入日志信息，该编辑器要么在个人配置文件中 通过以下命令设置 

git config --global core.editor

要么由以下环境变量之一设置： GIT_EDITOR、VISUAL 或 EDITOR。

2.10 编写提交信息# TOC

日志信息应当简洁但具有描述性。

第一行必须包含上下文、一个冒号以及对该提交所做事情的 非常简短的摘要。如有必要，可以添加细节， 并以空行分隔。除非包含代码，否则这些细节每行不应 超过 60-72 个字符。

一条良好提交信息的示例： 

avcodec/cbs: add a helper to read extradata within packet side data

Using ff_cbs_read() on the raw buffer will not parse it as extradata,
resulting in parsing errors for example when handling ISOBMFF avcC.
This helper works around that.

ptr might be NULL

如果第一行的摘要不够，请在信息正文中 解释你为何做出某项变更，你所做的内容大多数时候从变更本身 就显而易见。只说 "bug fix" 或 "10l" 是很糟糕的。请记住， 各种技能水平的人在阅读你的代码时都会查看并 从中学习。除了上下文之外，不要在日志信息中包含文件名， Git 会提供该信息。

如果该提交修复了一个已登记的问题，请在正文的单独一行中 说明：Fix Trac ticket #42.

第一行将被用于命名 补丁，由 git format-patch 完成。

在 git log --oneline 中常见的第一行错误 包括：开头缺少上下文；描述代码在补丁之前的行为； 行太长或折行到第二行。

2.11 准备补丁集# TOC

git format-patch <commit> [-o directory]

将为 <commit> 与 当前 HEAD 之间的每个提交生成一组补丁。例如 

git format-patch origin/master

将为当前分支上所有不存在于 上游中的提交生成补丁。 还有一个有用的快捷方式 

git format-patch -n

它会从最近 n 个提交生成补丁。 默认情况下，补丁在当前目录中创建。

2.12 发送补丁以供评审# TOC

git send-email <commit list|directory>

将发送由 git format-patch 创建的补丁，或直接 生成它们。所有电子邮件字段都可以在全局/本地 配置中设置，或通过在命令行中覆盖。 注意，该工具通常必须单独安装（例如基于 Debian 的发行版上的 git-email 软件包）。

2.13 重命名/移动/复制文件或文件内容# TOC

Git 会自动跟踪此类更改，将它们作为普通提交处理。 

mv/cp path/file otherpath/otherfile
git add [-A] .
git commit

3 Git 配置# TOC

为简化一些工作流程，建议同时配置 你的个人 Git 安装和本地 FFmpeg 仓库。

3.1 个人 Git 安装# TOC

将以下内容添加到 ~/.gitconfig，以帮助 git send-email 和 git format-patch 检测重命名： 

[diff]
        renames = copy

3.2 仓库配置# TOC

为了让 git send-email 自动将补丁发送 到 ffmpeg-devel 邮件列表，请将以下配置段添加 到 /path/to/ffmpeg/repository/.git/config： 

[sendemail]
        to = ffmpeg-devel@ffmpeg.org

4 FFmpeg 特有内容# TOC

4.1 回退有问题的提交# TOC

git reset <commit>

git reset 将撤销直到 <commit> 为止的更改提交，重写 当前分支的历史。 

git commit --amend

可以快速修改最后一次提交的详细信息。 

git rebase -i origin/master

将在主仓库之上重放本地提交，从而可以在这一过程中编辑、合并 或删除其中一些提交。

git reset、git commit --amend 和 git rebase 会重写历史，因此你应当只在本地分支或主题分支上使用它们。 主仓库将拒绝这些更改。 

git revert <commit>

git revert 将生成一个回退提交。这不会使 有问题的提交从历史中消失。

4.2 将变更推送到远端树# TOC

git push origin master --dry-run

将模拟把本地 master 分支推送到默认远端 （origin），并列出哪些分支、范围或提交原本会被 推送。 如果本地树和远端树 不同步，Git 会阻止你推送更改。参见 将源码树更新到最新修订版本。 

git remote add <name> <url>

将添加一个带名称引用的额外远端，如果你想 将本地分支推送到远端主机上进行评审，它会很有用。 

git push <remote> <refspec>

将把更改推送到 <remote> 仓库。 省略 <refspec> 会使 git push 更新所有与本地分支 匹配的远端分支。

4.3 查找特定的 svn 修订版本# TOC

从 1.7.1 版本起，Git 支持 ‘:/foo’ 语法，用于根据 正则表达式指定提交。参见 man gitrevisions 

git show :/'as revision 23456'

将显示 svn 变更集 ‘r23456’。对于较旧的 Git 版本，在 git log 输出中搜索是最简单的选择（尤其是当使用带有 搜索功能的分页器时）。

该提交可以用以下命令检出 

git checkout -b svn_23456 :/'as revision 23456'

或者对于 Git < 1.7.1，使用 

git checkout -b svn_23456 $SHA1

其中 $SHA1 是 git log 输出中的提交哈希。

5 gpg 密钥生成# TOC

如果你还没有 gpg 密钥，我们建议你创建一个基于 ed25519 的密钥，因为它 体积小、速度快且安全。尤其是在 git 中会产生较小的签名。 

gpg --default-new-key-algo "ed25519/cert,sign+cv25519/encr" --quick-generate-key "human@server.com"

生成密钥时，请确保指定的电子邮件地址与 git 中使用的电子邮件地址一致，因为像 github 这类网站会将不一致视为宣布此类提交未经验证的理由。生成密钥后，你 可以将其添加到 MAINTAINER 文件，并上传到密钥服务器。

6 推送前检查清单# TOC

一旦你有一组认为可以推送的提交， 就请逐项完成以下检查清单，以复核一切都处于 正确的顺序。该列表力求详尽。如果你只是 推送注释中的一个拼写错误，某些步骤可能没有必要。 请运用你的常识，但如有疑问，宁可谨慎行事。

首先，确保你将要推送的提交和分支 与你想要推送的内容一致，并且没有任何遗漏、多余或 错误的内容。你可以通过运行 git push 命令 并先加上 --dry-run 来查看将要推送的内容。然后检查用 git log -p 1234567..987654 列出的提交。git status 命令 可能有助于找出被遗忘添加的本地更改。

接下来，让代码完整跑一遍我们的测试套件。

  • make distclean
  • /path/to/ffmpeg/configure
  • make fate
  • 如果 fate 因缺少样本而失败，请运行 make fate-rsync 并重试

在推送之前，请确保你的所有更改都已检查过， 测试套件只检查回归，而且只是在一定程度上。它 显然不会检查新添加的功能/代码是否正常工作，除非你 为此添加了测试（推荐这样做）。

另请注意，每一个提交都应当通过测试套件，而不只是 一系列补丁的结果。

一旦全部通过，就把更改推送到你的公共 ffmpeg 克隆，并向 ffmpeg-devel 发送合并请求。你也可以直接推送它们，但这并不 推荐。
