1 简介# TOC

本文讨论的是 FFmpeg 自身的开发。有关在其他程序中使用 FFmpeg 库的信息可在别处找到，例如：

  • 已安装的头文件
  • Doxygen 文档 由头文件生成
  • doc/examples 下的示例

有关在外部程序中使用 FFmpeg 的更详细法律信息，请阅读 源码树中的 LICENSE 文件，并查阅 https://ffmpeg.org/legal.html。

如果你为自己的使用场景修改了 FFmpeg 代码，我们强烈建议你 把改动提交回给我们，并以本文档作为指南。这样做既有 务实的理由，也有理念上的理由：

  • 维护外部改动以跟上上游开发既 耗时又容易出错。把你的代码放进主源码树，它就会 由 FFmpeg 开发者维护。
  • FFmpeg 开发者中包括该领域的顶尖专家，他们能发现你的代码中的缺陷或 设计缺陷。
  • 通过支持你认为有用的项目，你能确保它持续得到 维护和开发。

所有提议的代码改动都应当提交到 Forgejo 或 开发邮件列表进行评审，具体 说明详见提交补丁一章。代码 应当符合开发政策并遵循编码规则。 提交代码的开发者和作者要对各自的改动负责， 并应当设法修复其提交所引发的问题。

2 编码规则# TOC

2.1 语言# TOC

FFmpeg 主要使用 ISO C11 语言编写，但公共 头文件必须保持 C99 兼容。

在有充分理由时可以使用编译器特定的扩展，但不得 依赖这些扩展，也就是说，代码必须仍能使用缺少 该扩展的编译器编译并运行。

代码库中的任何位置都不得使用以下 C99 特性：

  • 变长数组；
  • 复数；

2.1.1 SIMD/DSP# TOC

由于现代编译器无法从纯 C 代码生成高效的 SIMD 或其他 对性能至关重要的 DSP 代码，因此使用手写汇编。 通常这类代码被隔离在一个单独的函数中。此时标准做法是 为该函数编写多个版本——一个可在任何环境下工作、 也可能有助于调试的纯 C 版本，以及可能的多个 针对特定架构的优化实现。随后初始化代码会 在运行时选择可用的最佳版本，并将其载入一个函数 指针；该函数此后总是通过这个指针调用。

编写汇编时使用的具体语法为：

  • x86 上使用 NASM；
  • ARM 和 RISC-V 上使用 GAS。

一个用于汇编的单元测试框架名为 checkasm，位于 tests/checkasm 下。所有新的汇编都应当附带 checkasm 测试； 为缺少测试的现有汇编补充测试也受到强烈鼓励。

2.1.2 其他语言# TOC

在特殊情况下可以使用 C 以外的其他语言：

  • 当相关代码无法按 SIMD/DSP 一节所述的 标准方式编写时，可使用编译器内建函数或内联汇编。这 通常适用于需要内联的代码。
  • 在与 macOS 特定接口交互时需要使用的 Objective-C。

2.2 代码格式化约定# TOC

关于文件中的代码风格，有以下准则：

  • 缩进大小为 4。
  • 在 Makefiles 之外禁止使用制表符，任何 形式的行尾空白字符同样被禁止。包含其中任何一种的提交都会被 git 仓库拒绝。
  • 你应当尽量把代码行限制在 80 个字符以内；但只有在这样做 确实能提高可读性时才应如此。
  • 使用 K&R 代码风格。

这种呈现方式受 ’indent -i4 -kr -nut’ 启发。

2.2.1 示例# TOC

一些值得注意的示例，用于说明 FFmpeg 中常见的代码风格：

  • 赋值运算符两侧以及 if/do/while/for 关键字之后要有空格： 
    // Good
if (condition)
    av_foo();

    // Good
for (size_t i = 0; i < len; i++)
    av_bar(i);

    // Good
size_t size = 0;

    不过，括号与条件之间不要加空格，除非这样有助于 复杂条件的可读性，因此不应像下面这样写： 

    // Bad style
if ( condition )
    av_foo();
  • 不要使用不必要的括号，除非这样有助于可读性： 
    // Good
int fields = ilace ? 2 : 1;
  • 不要用花括号包裹单行语句块。只有在有配套的 else 语句时才使用花括号。这样便于日后追踪代码改动。 
    // Good
if (bits_pixel == 24) {
    avctx->pix_fmt = AV_PIX_FMT_BGR24;
} else if (bits_pixel == 8) {
    avctx->pix_fmt = AV_PIX_FMT_GRAY8;
} else
    return AVERROR_INVALIDDATA;
  • 在合适的情况下避免在条件中赋值： 
    // Good
video_enc->chroma_intra_matrix = av_mallocz(sizeof(*video_enc->chroma_intra_matrix) * 64)
if (!video_enc->chroma_intra_matrix)
    return AVERROR(ENOMEM);

    // Bad style
if (!(video_enc->chroma_intra_matrix = av_mallocz(sizeof(*video_enc->chroma_intra_matrix) * 64)))
    return AVERROR(ENOMEM);

    // Ok
while ((entry = av_dict_iterate(options, entry)))
    av_log(ctx, AV_LOG_INFO, "Item '%s': '%s'\n", entry->key, entry->value);
  • 声明指针变量时，* 属于变量而非类型： 
    // Good
AVStream *stream;

    // Bad style
AVStream* stream;
  • 在合理的情况下，优先使用较小的变量作用域，尤其是在 for 循环中： 
    // Good
for (unsigned i = 0; i < submix->nb_elements; i++) {
    // Do something...
}

    // Bad style
unsigned i;
//...
for (i = 0; i < submix->nb_elements; i++) {
    // Do something...
}

如果你处理的文件并未始终遵循这些准则， 请把你正在编辑的部分改为遵循这些准则，但不要 为了让文件符合这些准则而在文件中做无关的改动。

2.2.2 Vim 配置# TOC

为了让 Vim 遵循 FFmpeg 的格式化约定，请把 以下片段粘贴到你的 .vimrc 中： 

" indentation rules for FFmpeg: 4 spaces, no tabs
set expandtab
set shiftwidth=4
set softtabstop=4
set cindent
set cinoptions=(0
" Allow tabs in Makefiles.
autocmd FileType make,automake set noexpandtab shiftwidth=8 softtabstop=8
" Trailing whitespace and tabs are forbidden, so highlight them.
highlight ForbiddenWhitespace ctermbg=red guibg=red
match ForbiddenWhitespace /\s\+$\|\t/
" Do not highlight spaces at the end of line while typing on that line.
autocmd InsertEnter * match ForbiddenWhitespace /\t\|\s\+\%#\@<!$/

2.3 注释# TOC

使用 JavaDoc/Doxygen 格式（参见下面的示例），以便代码文档 能够自动生成。所有非平凡函数上方都应当有注释， 说明该函数的作用，即使只有一句话。 所有结构体及其成员变量也应当有文档。

避免使用 Qt 风格以及类似的、其中含有 ! 的 Doxygen 语法，即把 //! 替换为 /// 等。此外，标记命令应当采用 @ 语法， 即使用 @param 而不是 \param。 

/**
 * @file
 * MPEG codec.
 * @author ...
 */

/**
 * Summary sentence.
 * more text ...
 * ...
 */
typedef struct Foobar {
    int var1; /**< var1 description */
    int var2; ///< var2 description
    /** var3 description */
    int var3;
} Foobar;

/**
 * Summary sentence.
 * more text ...
 * ...
 * @param my_parameter description of my_parameter
 * @return return value description
 */
int myfunc(int my_parameter)
...

2.4 命名约定# TOC

函数、变量和结构体成员的名称必须小写，使用 下划线（_）分隔单词。例如，‘avfilter_get_video_buffer’ 是可接受的函数名，而 ‘AVFilterGetVideo’ 则不是。

结构体、联合体、枚举以及经 typedef 的类型名必须使用 CamelCase。所有结构体 和联合体都应当 typedef 为与结构体/联合体标签相同的名称，例如 typedef struct AVFoo { ... } AVFoo;。枚举通常不 进行 typedef。

枚举常量和宏必须使用大写，但伪装成 函数的宏除外，它们应当采用函数的命名约定。

库中的所有标识符应当按如下方式设置命名空间：

  • 文件和更低作用域的标识符（例如局部变量、 静态函数）以及结构体和联合体成员不需要命名空间，
  • 对于在文件作用域之外可见、但仅在单个库内部使用的变量和函数，必须使用 ff_ 前缀，例如 ‘ff_w64_demuxer’。这样当 FFmpeg 被静态链接时可避免 名称冲突。
  • 对于在文件作用域之外可见、跨多个库内部使用的变量和函数， 请使用 avpriv_ 作为前缀，例如 ‘avpriv_report_missing_feature’。
  • 所有其它内部标识符，例如私有类型名或宏名，设置命名空间只是为了 避免可能的内部冲突。例如 H264_NAL_SPS 与 HEVC_NAL_SPS。
  • 除了常用的 av_ 之外，每个库的公开符号还有自己的前缀 （libavformat 用 avformat_， libavcodec 用 avcodec_，libswresample 用 swr_ 等等）。 请查看现有代码并据此选择名称。
  • 其它公开标识符（结构体、联合体、枚举、宏、类型名）必须使用其 所属库的公开前缀（AV、Sws 或 Swr）。

此外，不应侵占为系统保留的名称空间。 以 _t 结尾的标识符由 POSIX 保留。 还要避免使用以 __ 开头，或以 _ 后跟大写字母开头的名称， 因为它们由 C 标准保留。以 _ 开头的名称 在文件层级被保留，不得用于对外可见的 符号。如有疑问，干脆完全避免使用以 _ 开头的名称。

2.5 其他约定# TOC

  • 只有在必要时才应使用强制类型转换。如果多余的括号 不能让代码更易理解，也应当避免使用。
  • 在适用的情况下，应当使用 SI 单位。例如超时应当以秒为基本单位，而不是微秒。 这意味着像 ‘1.0’ 这样的裸值必须表示 1 秒，‘50m’ 表示 50 毫秒。重量则应当使用克。

3 开发政策# TOC

3.1 代码行为# TOC

代码必须是有效的。它不得崩溃、中止、访问无效指针、泄漏 内存、导致数据竞争或有符号整数溢出，或以其它方式造成 未定义行为。应当检查错误码，并在适用时 将其转发给调用者。

我们的库可能被同一进程中的多个相互独立的调用者调用。 这些调用可能来自任意数量的线程，而且不同调用点 可能彼此并不知晓——例如，某个用户程序可能直接调用我们的 库，同时又使用了一个或多个同样会调用我们库的库。 代码在此类条件下必须表现正确。

代码必须把从调用者接收的、或从文件、网络等读取的任何字节流 视为不可信。任意输入都绝不能导致不安全的 行为或安全问题。

对于常见格式和编解码器的常见实际错误，应当在可行时检测， 在适当时报告，并加以处理以尽可能产生最佳输出， 例如通过错误隐藏。

所有错误仍必须被安全处理，但如果这些错误被检测到， 是否报告或如何处理则交由实现决定。

代码必须使用 av_malloc() 系列函数，它们来自 libavutil/mem.h，以完成所有内存分配，特殊情况除外 （例如与要求使用特定 分配器的外部库交互时）。

所有分配都应当检查，失败时返回 AVERROR(ENOMEM)。 常见错误是错误处理路径会泄漏内存——请确保 不会发生这种情况。

我们的库不得直接访问 stdio 流 stdin/stdout/stderr （例如通过 printf() 系列函数），因为这不是库安全的。对于 日志记录，请使用 av_log()。

3.2 补丁/提交# TOC

贡献的代码应当以下列许可证授权： LGPL 2.1， 并包含 "or any later version" 条款；或者，如果你更倾向于 赠与式许可证，也可以采用 ISC 或 MIT 许可证。 GPL 2（包含 "or any later version" 条款）也是可以接受的，但首选 LGPL。 如果你新增文件，请为其加上合适的许可证头部。不要从随意的 地方复制粘贴，请以现有文件作为模板。

这指的是已启用且会破坏编译的未完成代码， 或者是能编译但不能工作、会破坏回归测试的代码。未完成 但已禁用的代码在特定情况下可能被允许，例如 缺少样本，或只实现了一小部分特性的实现。 在推送之前，务必查看邮件列表中是否有评审者提出异议，并测试 FATE。

提交信息是告知其他开发者某个改动做了什么以及为什么做的 极为重要的工具。每个提交都必须始终带有填写规范的 提交信息，格式如下： 

area changed: short 1 line description

details describing what and why and giving references.

如果该提交解决了我们缺陷跟踪系统上的已知缺陷或其它外部问题 （例如 CVE），提交信息中应当包含相关的缺陷 ID 或其它 外部标识符。注意，这应当是在给出恰当解释之外的补充，而不是 替代解释。诸如 "fixed!" 或 "Changed it." 这样的评论 是不可接受的。

应用已在邮件列表中充分讨论过的补丁时， 请在提交信息中引用该讨论帖。

如果它对你和他人有效，并且通过了 FATE，那么在满足其它提交 标准的前提下，提交它是可以的。你不必担心 测试过度。如果你的代码有问题（可移植性、触发 编译器缺陷、异常环境等），它们会被报告并最终 修复。

应当把它们拆分成自包含的部分。另外别忘了， 如果部分 B 依赖部分 A，而 A 不依赖 B，那么 A 可以 并且应当先于 B 单独提交。把改动很好地 拆分成自包含的部分，能让在提交日志邮件列表上评审和理解它们 变得更容易。这在日后调试时 也有帮助。 另外，如果你对是否要拆分存有疑虑，请不要犹豫， 在开发者邮件列表上提问/讨论。

在完整修复所报告问题的前提下，缺陷修复应尽可能小。 对于正确性或健壮性并非必需的改动应当单独提交， 尤其是当它们会增加复杂度或影响向后移植时。

如果源码缩进和其它表面性改动与功能性改动混在一起，我们会拒绝， 此类提交将被拒绝并移除。不过， 能被 git diff --ignore-all-space 忽略的缩进改动 （例如空白字符数量的变化、行首/行尾空格）可以与 功能性改动混在一起，因为评审者可以用 git diff -w 或 git log -p --ignore-all-space 只评审改动中的功能性 部分。Forgejo 的拉取请求界面也提供了 “Hide whitespace changes” 选项用于此目的。每位 开发者都有自己的缩进风格，你不应改动它。当然， 如果你（重）写某些内容，可以使用自己的风格，尽管我们更 希望整个 FFmpeg 的缩进是一致的（许多项目 强制规定某种缩进风格——我们不这样做。）。如果你确实需要做 非空白的表面性改动，请把它们与真正的改动严格分开。

注意：如果你不得不把 if(){ .. } 加在一大段（> 5 行）代码之上， 那么要么不要改动其中内部部分的缩进（不要 把它向右移）！要么在单独的提交中这么做

请确保提交的作者设置正确。（参见 git commit –author） 如果你应用了补丁，请发送 一封回复到 ffmpeg-devel（或你获取该补丁的地方），说明 你已应用该补丁。

如果某个提交/补丁修复了某位研究人员发现的问题，请务必在提交信息中 署明该研究人员发现/报告了该问题。

未经许可，切勿向他人积极维护的代码提交改动。 请把补丁发送到 ffmpeg-devel。如果在一段合理的 时间内无人回复（构建失败和安全修复为 12 小时，小改动为 3 天， 大补丁为 1 周），那么如果你认为没问题就可以提交你的补丁。 另请注意，维护者完全可以直接要求更多的评审时间！

3.3 代码# TOC

编译器警告表示潜在的缺陷或风格不佳的代码。如果某类 警告总是指向正确且整洁的代码，那么就应当禁用该警告， 而不是改动代码。 因此，剩下的警告要么是缺陷，要么是正确代码。 如果是缺陷，就必须修复该缺陷。如果不是，则应当改动 代码使其不再产生警告，除非那样做会导致性能下降 或使代码晦涩难懂。

3.4 库的公共接口# TOC

FFmpeg 中的每个库都在其已安装的头文件中提供一组公开 API， 这些 API 就是列在该库的 Makefile 中变量 HEADERS 里的那些。在这些头文件中定义的所有标识符 （除明确另有说明的以外），以及从编译后的共享库或静态库中导出的 相应符号，都被视为公开接口，并且必须 遵守本节所述的 API 与 ABI 兼容性规则。

公开 API 在给定的主版本内必须向后兼容。也就是说，任何 能在某个库版本下编译并正常运行的合法用户代码，必须仍然 能在任何后续版本下编译并正常运行，只要主版本号 未变。这里的 "合法用户代码" 指以有文档记载和/或预期的方式调用我们的 API， 并且不依赖任何未定义行为的代码。 提升主版本号可能会破坏向后兼容性，但仅限于 主版本号提升 中所述的范围。

我们还保证共享库和静态库的 ABI 向后兼容性。 也就是说，应当能够用一个后续版本的构建替换我们库的共享或静态构建 （在静态库的情况下需要重新链接用户二进制文件），而不会破坏任何合法的用户二进制文件， 只要主版本号 保持不变。

3.4.1 新增接口# TOC

已安装头文件中的任何新公开标识符都被视为新 API——这 包括新函数、结构体、宏、枚举值、typedef，现有结构体中的新字段、 新的已安装头文件等。添加新 API 时请考虑以下 准则。

虽然添加新 API 相对容易，但由于上述兼容性要求， 改动或移除它们要困难得多。因此，你应当 仔细考虑你所添加的功能是否真的需要 作为新公开 API 暴露给我们的调用者。

你的新 API 应当至少有一个库之外的成熟用例， 且该用例无法用现有 API 轻易实现。FFmpeg 中的每个库 也有明确的范围——你的新 API 必须落在其中。

如果你的新 API 用于替换现有 API，它应当严格优于后者， 使得使用新 API 的收益大于 调用者改动其代码的代价。添加新 API 之后，你应当 弃用旧 API 并安排将其移除，如 移除接口 所述。

如果你认为某个现有 API 有缺陷并想修复它，大多数情况下的首选做法 是添加一个命名不同的替代品，并弃用 现有 API，而不是修改它。重要的是让改动对我们的调用者可见 （例如通过编译期或运行期的弃用警告），并 清楚地说明如何迁移到新 API（例如在 Doxygen 文档或 wiki 上）。

各类调用者使用 FFmpeg 库来执行各种 多媒体相关的处理任务。因此，你应当在合理的范围内，尽量 让新 API 面向尽可能广泛的用例，并避免 不必要地把它限制在某一类调用者上（例如仅限媒体 播放或仅限转码）。

检查 FFmpeg 中是否已存在类似的 API。如果存在，请尽量参照 它们来设计你的新增内容，以获得更好的整体一致性。

新标识符的命名应当遵循 命名约定， 并在适用时与其它类似 API 保持一致。

你还应当考虑你的 API 将来如何以向后兼容的方式 进行扩展。如果你要添加新的结构体 AVFoo， 标准做法是要求调用者始终通过一个 构造函数（通常命名为 av_foo_alloc()）来分配它。这样新增字段 就可以添加到结构体末尾而不破坏 ABI 兼容性。 通常你还需要一个析构函数——av_foo_free(AVFoo**)，它 释放间接传入的对象（及其内容，如适用），并 向传入的指针写入 NULL，从而消除调用者内存中潜在的 悬空指针。

如果你要添加新函数，请考虑将来是否可能需要调整 它们的行为——你可能想添加一个 flags 参数，即使 它最初并不会被使用。

所有新 API 都必须以 Doxygen 格式的注释记录在 你添加到公开头文件中的标识符上方。你还应当简要地在 doc/APIchanges 中提及该改动。

向后不兼容的 API 或 ABI 变更需要递增（提升） 主版本号，如 主版本号提升 所述。主版本 提升是按规定日程发生的重大事件 —— 因此如果你的变更 确实需要一次主版本提升，你应当将其置于 #if 预处理保护之下， 使其在下一次主版本提升到来之前保持禁用。

可以在不破坏 API 或 ABI 兼容性的情况下新增的新 API，需要 递增次版本号。

递增第三个（微）版本组成部分意味着一次值得注意的二进制 兼容变更（例如对解码器有影响的编码器缺陷修复）。第三个 组成部分始终从 100 开始，以区分 FFmpeg 与 Libav。

3.4.2 移除接口# TOC

由于上述兼容性保证，移除 API 是一个复杂的 过程，只应当在有充分理由时才进行。通常，一个有缺陷、 限制过多或在其他方面不够完善的 API 会被更优的 API 取代，不过 有时确实会出现我们在没有任何替代方案的情况下移除某个 API 的情况（例如当 它所提供的功能被认为不值得付出维护成本、超出项目 范围、存在根本性缺陷等）。

移除分两步 —— 首先将该 API 标记为弃用并安排 移除，但它仍然存在且可用。第二步才是真正 移除该 API —— 这在 主版本号提升 中有描述。

要弃用一个 API，你应当向用户发出信号，表明他们应当停止使用 它。例如，如果你打算移除结构体成员或函数，你应当用 attribute_deprecated 标记它们。当无法这样做时，或许可以 在运行时检测到对已弃用 API 的使用并打印一条警告 （但要注意不要过于频繁地打印）。你还应当记录该弃用 （以及替代方案，如果适用），写在相关的 Doxygen 文档块中。

最后，你应当定义一个类似下面这样的弃用保护宏 #define FF_API_<FOO> (LIBAVBAR_VERSION_MAJOR < XX)（其中 XX 是该 API 将被移除的 主版本号），位置在 libavbar/version_major.h （对于 libavutil 则是 version.h）。然后用 #if FF_API_<FOO> .... #endif 包裹所有对已弃用 API 的使用，这样代码会在 主版本号达到 XX 后自动被禁用。你还可以使用 FF_DISABLE_DEPRECATION_WARNINGS 和 FF_ENABLE_DEPRECATION_WARNINGS 来在这些保护宏内部抑制编译器弃用警告。你应当测试 代码在保护宏求值为 true 和 false 两种情况下都能编译并正常工作。

3.4.3 主版本号提升# TOC

主版本号提升意味着 API 和/或 ABI 兼容性的破坏。为了减少 对调用方（它们需要调整自己的代码）的负面影响， 主版本提升期间的向后不兼容变更应当仅限于：

  • 移除先前已弃用的 API。
  • 执行破坏 ABI 但不破坏 API 的变更，例如重新排列结构体内容。

4 提交补丁# TOC

首先，如果你还没有读过上面的 编码规则，请先阅读，特别是 关于补丁提交的规则。

提交补丁时，请使用 git format-patch 或 git send-email。我们无法阅读其他形式的差异 :-)。

另外，请不要提交包含多个不相关变更的补丁。 请把它拆分成独立的、自成一体的片段。这并不意味着按文件 逐个拆分。相反，请让补丁尽可能小，同时仍然 把它保持为一个包含单个变更的逻辑单元，即使 该变更跨越多个文件。这使我们评审你的补丁容易得多， 并大大增加你的补丁被接受应用的机会。

使用 FFmpeg 的 patcheck 工具来检查你的补丁。 该工具位于 tools 目录中。

在提交补丁之前运行 回归测试，以验证 它不会引起意外问题。

如果你告诉我们该补丁做了什么（例如 ’用 lrintf 替换 lrint’），以及为什么（例如 ’*BSD 不符合 C99 且没有 lrint()’），也会很有帮助。

另外，如果你要发送多个补丁，请把每个补丁作为单独的邮件发送， 不要在同一封邮件中附加多个不相关的补丁。

补丁应当发布到 Forgejo 或 ffmpeg-devel 邮件列表。尽可能使用 git send-email，因为它能正确地 发送补丁，无需额外小心处理。如果你做不到，那就把补丁作为 base64 编码的附件发送，这样你的补丁在传输过程中 不会被破坏。同时确保使用正确的 mime 类型 （text/x-diff、text/x-patch，或者至少 text/plain），并且每封邮件只有 一个补丁内联或作为附件。 你可以查看 https://patchwork.ffmpeg.org，如果你的补丁没有出现，很可能是它的 mime 类型 有误。

请参见 https://git-send-email.io/。 对于 gmail，另请参见 https://shallowsky.com/blog/tech/email/gmail-app-passwds.html。

使用 git send-email 可能并非对每个人都合适。下面 这个技巧可以让你通过电子邮件客户端以安全的 方式发送补丁。它已在 Outlook 和 Thunderbird（配合 X-Unsent 扩展）上测试过，可能也适用于其他应用程序。

像这样创建你的补丁： 

git format-patch -s -o "outputfolder" --add-header "X-Unsent: 1" --suffix .eml --to ffmpeg-devel@ffmpeg.org -1 1a2b3c4d

现在你只需用电子邮件应用程序打开该 eml 文件， 然后执行 ’Send’。

你的补丁或拉取请求将在邮件列表或 code.ffmpeg.org 上接受评审。你很可能会被要求 做一些修改，并需要提交一个包含了评审意见中 各项要求的改进版本。这个过程可能会经历 多次迭代。一旦你的补丁被认为足够好，某位开发者 会接手它并将其提交到官方的 FFmpeg 源码树中。 如果你想要基于 LLM 的评审，请把 Forgejo Fairy 添加为评审者 到你的拉取请求中。关于 Fairy 自身的问题可以在她的 仓库 中报告。

请给我们几天时间作出回应。但如果过了一段时间没有回应， 请通过电子邮件发送提醒。你的补丁最终应当会得到处理。

7 补丁评审流程# TOC

所有发布到 ffmpeg-devel 的补丁都会被评审，除非它们包含 明确说明该补丁不是针对 git master 分支的备注。 评审意见和评论将作为对该补丁的回复发布在 邮件列表上。补丁提交者随后必须处理每一条评论， 这可以通过重新提交修改后的补丁或通过讨论来完成。重新提交的 补丁本身也会像其他补丁一样被评审。如果在某个时候 一个补丁在没有任何评论的情况下通过评审，那么它就被批准了， 对于简单的小补丁这可以立即发生，而大型补丁通常 必须经过多次修改和评审才能被批准。 补丁被批准后会被提交到仓库中。

我们会评审所有提交的补丁，但有时我们非常忙，因此 尤其是大型补丁，这可能要花上几周时间。

如果你觉得评审流程太慢，并且愿意尝试 接管你所修改代码区域的维护工作，那么只需克隆 git master 并在那里维护该代码区域。我们会从 维护得最好的地方合并每个区域。

重新提交补丁时，请不要做出任何与评审期间收到的 评论无关的重大变更。这类补丁会 被拒绝。相反，请把重大变更或新功能作为 单独的补丁提交。

欢迎所有人评审补丁。另外，如果你正在等待你的补丁 被评审，请考虑帮忙评审其他补丁，这是让所有人的补丁 更快得到评审的好办法。

如果你需要上传样本，请发送邮件到 samples-request。

8.2 可视化测试覆盖率# TOC

FFmpeg 构建系统可以借助覆盖率工具轻松 gcov/lcov 可视化测试覆盖率。这涉及 以下步骤：

  1. 配置为启用插桩进行编译： configure --toolchain=gcov.
  2. 运行你的测试用例，可以手动运行，也可以通过 FATE 运行。这既可以是 完整的 FATE 回归测试套件，也可以是对 FFmpeg 提供的 任意前端工具的任意调用，任意组合均可。
  3. 运行 make lcov 生成 HTML 格式的覆盖率数据。
  4. 用你偏好的 HTML 查看器查看 lcov/index.html。

你可以使用命令 make lcov-reset 重置覆盖率 测量数据。在运行一项 新测试之后，你需要重新运行 make lcov。

8.3 使用 Valgrind# TOC

configure 脚本提供了一种使用 valgrind 查找与内存处理 相关的缺陷的捷径。只需在 configure 命令行中 添加 --toolchain=valgrind-memcheck 或 --toolchain=valgrind-massif 选项，就会为在 valgrind 套件的 memcheck 或 massif 工具的监督下运行 FATE 设置合理的默认值。

如果你需要更精细地控制 valgrind 的调用方式，请改用 --target-exec='valgrind <your_custom_valgrind_options> 选项，写在 你的 configure 命令行中。

9.2 成为维护者# TOC

人们通过像发送任何其他代码变更一样发送补丁，把自己加入 MAINTAINERS。 这些补丁会像其他任何补丁一样由社区评审。我们希望 如果某人对新的维护者有异议，她愿意 公开以她的全名提出异议，并愿意接管该领域的维护工作。

10 发布流程# TOC

FFmpeg 维护着一组 发布分支，它们是 推荐给系统集成商和发行商（例如 Linux 发行版等）的交付产物。在固定时间，一位 发布 管理者会准备、测试并发布 tarball 到 https://ffmpeg.org 网站上。

发布分为两种：

  1. 主版本发布总是包含最新最出色的 特性和功能。
  2. 点发布是从 release 分支上切分出来的， 这些分支命名为 release/X，其中 X 是发布 版本号。

请注意，我们向用户承诺，任何 FFmpeg 发布版本的共享库 在任何情况下都不会破坏针对 同一发布系列 先前版本编译的程序！

不过，我们有时确实会做出需要在应用程序中 进行适配的 API 变更，这类变更只允许在（新的）主版本发布中进行，并且 还需要进一步的步骤，例如提升库版本号和/或 调整符号版本控制文件。请就这类变更及时在 ffmpeg-devel 邮件列表上讨论，以便提前规划。

10.1 点版本发布的标准# TOC

符合以下准则的变更是纳入点发布的 有效候选：

  1. 修复安全问题，最好是由一个 CVE 编号（由 http://cve.mitre.org/ 分配）来标识。
  2. 修复 https://trac.ffmpeg.org 中已记录的缺陷。
  3. 改进随附的文档。
  4. 保持与同一发布分支先前 点发布的源代码和二进制兼容性。

检查这些规则的顺序是 (1 OR 2 OR 3) AND 4。

10.2 发布检查清单# TOC

发布过程包含以下步骤：

  1. 确保 RELEASE 文件包含即将发布版本的 版本号。
  2. 在 https://trac.ffmpeg.org/admin/ticket/versions 处添加该发布。
  3. 向邮件列表宣布将要进行发布的意图。
  4. 确保所有相关的安全修复都已被回溯移植。参见 https://ffmpeg.org/security.html。
  5. 确保 FATE 回归测试套件在发布 分支上至少在 i386 和 amd64 上仍然通过 （参见 回归测试）。
  6. 准备 bz2 和 gz 格式的发布 tarball，并 补充包含 gpg 签名的文件
  7. 在 https://ffmpeg.org/releases 处发布这些 tarball。创建并 推送形如 nX 的附注标签，其中 X 包含版本号。
  8. 向 ffmpeg-devel 邮件列表提议并发送一个补丁， 其中包含给网站用的新闻条目。
  9. 发布该新闻条目。
  10. 向邮件列表发送公告。
